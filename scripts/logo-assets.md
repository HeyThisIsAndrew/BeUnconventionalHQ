# Logo assets — export spec

What to hand over when the logo changes, and why each number is what it is.
Two files are requested: the **lockup** (replaces the site-wide logo) and the
**crown** (a dedicated navbar mark). Read "Why the navbar looks like mush"
first — it explains why the second file exists.

---

## Current state of the assets

| File | Pixels | Opaque artwork | Notes |
| --- | --- | --- | --- |
| `src/assets/logo.webp` | 2000 × 2000 | 1909 × 832, sitting 421px down | Square canvas. ~42% of the height is artwork; the rest is transparent padding, **off-centre**. |
| `src/assets/logo-mark.webp` | 1981 × 911 | 1909 × 832 + 36px even margin | Same artwork, pre-cropped. This is the good one. |

`logo.webp` also carries a soft outer glow that reaches to an alpha bounding
box of 1957 × 1333 — nearly invisible, but it defeats any automatic trim.
Don't ship a glow in the new files (see the export settings).

## Why the navbar looks like mush

The navbar renders `logo.webp` — the **square** file — inside a box that is
36–45px tall (`.nav-logo img` in `src/styles/modules/navbar.css`). Because the
artwork is only 41.6% of that square's height, the lockup is actually drawn at
about **19px tall**: a crown, a two-tier wordmark, and a 6pt tagline, all
inside 19 pixels. No compression setting or file swap fixes that — it's a
geometry problem.

Pointing the navbar at `logo-mark.webp` instead makes the artwork 2.4× bigger
for free, and is the right interim fix. But even at a perfect 45px the tagline
line ("SOMETIMES UNCONVENTIONAL IS THE ONLY WAY FORWARD.") renders around
2.5px tall — still illegible, still reads as texture. The lockup is a
three-tier design; it needs ~120px of height to work. The navbar has 45.

Hence the crown.

## File A — the lockup (required)

Replaces `src/assets/logo-mark.webp` and, on the same pass, retires
`src/assets/logo.webp`. **One file covers both** — the square version has no
job that the tight-cropped version doesn't do better.

| Setting | Value |
| --- | --- |
| Format | **PNG-24** (not WebP, not JPEG) |
| Bit depth | 8 bits/channel |
| Transparency | **On** |
| Colour space | sRGB — "Convert to sRGB" checked |
| Metadata | None |
| Width | **2000 px** |
| Height | Whatever the artwork's own proportions produce. Do not pad it to a round number. |
| Padding | **None.** Trim tight to the artwork. |
| Effects | **No outer glow, no drop shadow.** The site draws its own glow in CSS. |
| Filename | `logo-lockup-2000.png` |

Photoshop steps:

1. `Image → Trim…` → **Transparent Pixels**, all four sides checked. Run this
   *before* resizing, and make sure any glow/shadow layer is off first or the
   trim will stop at the glow instead of the ink.
2. `Image → Image Size…` → Width 2000 px, constrain proportions,
   Resample: **Bicubic Sharper** if reducing, **Preserve Details 2.0** if
   enlarging.
3. `File → Export → Export As…` → PNG, **Transparency ✓**,
   **"Smaller File (8-bit)" unchecked**, Metadata: None, Colour Space:
   Convert to sRGB ✓.

Why 2000 px wide: the largest on-screen use is the footer at 300 CSS px (600px
on a 2× display), and the press-kit PDF prints it at 0.45in. The true floor is
about 700px; 2000 gives print headroom and matches the current source, so
nothing about build cost or quality changes.

Why PNG and not WebP: everything under `src/assets/` goes through sharp at
build time (`imageService: 'compile'` in `astro.config.mjs`) and is re-encoded
to WebP per size. Handing over WebP would compress it twice. PNG in, WebP out,
one generation of loss instead of two.

### ⚠️ Tell me the exported pixel dimensions

Changing the bottom of the lockup changes its **aspect ratio**, and that ratio
is hardcoded in eight places as matched `width`/`height` pairs — `600×276` in
`Footer.astro`, `520×239` in `IntelMagazine.astro`, `440×202` and `240×110` in
`ArticleThumb.astro`, and so on. Those pairs are what reserve the right box
before the image loads; if they don't match the new file, the page shifts as
it loads and the CLS score regresses. So send the exact `W × H` of the
exported PNG and I'll recompute every one of them.

## File B — the crown (recommended, for the navbar)

### Preferred: SVG

A crown is a single line-drawn form — it's the one thing on this site that
genuinely wants to be a vector. Inlined, it costs **zero network requests**,
stays sharp at any size and on any display, and can be recoloured in CSS. It
also lets `favicon.svg` (currently a hand-approximated geometric crown that
doesn't match the real artwork), the 180×180 apple-touch icon and the navbar
all be cut from one source.

| Requirement | Value |
| --- | --- |
| `viewBox` | Present, tight to the path bounds |
| `width` / `height` attrs | Omit — CSS sizes it |
| Fill | `currentColor` if possible, otherwise `#ffffff` |
| Contents | Paths only. **No embedded raster image**, no `<style>` block, no clip paths |
| Size | Under 10 KB minified |
| Filename | `crown.svg` |

Caveat worth knowing before you spend time on it: the crown is **brush art
with rough, broken edges**, and Photoshop's `Export As → SVG` on a raster
layer just wraps a bitmap in an `<svg>` tag — that produces a file that is
technically SVG and practically useless. Real vector means either (a) the
crown already exists as a shape/path layer, or (b) an Illustrator
`Image Trace` at a high-fidelity preset, expanded, with the roughness
preserved rather than smoothed away. If neither is quick, send the PNG below —
it's a perfectly good outcome, not a fallback with a penalty.

### PNG alternative

| Setting | Value |
| --- | --- |
| Format | PNG-24, 8 bits/channel |
| Transparency | On |
| Colour space | sRGB, metadata none |
| Height | **600 px** |
| Width | Natural (~900 px at the crown's roughly 1.5:1 proportions) |
| Padding | None — trim tight |
| Colour | White, as it appears in the lockup |
| Filename | `crown-600.png` |

600px tall is deliberate overkill: the navbar draws it at ~44px, so 3× DPR
needs only 132px. The extra headroom is so the same file can cut the 180×180
home-screen icon and the favicon without a second export. If you'd rather keep
it minimal, 180px tall is the real floor for the navbar alone.

### Optional: a dark variant

The crown is white, which works everywhere on this site (dark theme
throughout) but not on the white press-kit PDF or a light-background favicon.
A `crown-dark-600.png` / `crown-dark.svg` in `#0d0d0f` would close that gap.
Not needed for the navbar work.

## What the navbar becomes

Crown at the current 36–45px box, filling it properly instead of at 42%. The
crown's ~1.5:1 proportions put it at roughly 68px wide at full height, against
the 45px the square file occupies now — so the header's horizontal balance
barely moves.

The brand name is not lost. `Navbar.astro` already renders a text lockup
(`#nav-identity`: BE / UNCONVENTIONAL / HQ) that fades in on scroll, and the
`alt` attribute carries the full name for screen readers and crawlers. The one
gap is the top of the page before any scroll, where the nav would show a lone
crown — closed by showing that text lockup at rest on desktop, which is a CSS
change to an element that already exists and already has its type styled.

## Performance guardrails

These hold regardless of which files arrive.

- **Source size is not payload.** `imageService: 'compile'` runs sharp at build
  time and emits sized static WebP; the 2000px PNG never reaches a browser.
  Keep it under ~2 MB anyway so the repo and build stay quick.
- **Every `<Image>` keeps an explicit `width` + `height`** matching the new
  ratio. This is the CLS contract — see the warning under File A.
- **The navbar image stays `loading="eager"`** and small. It's above the fold
  on every route and sits in the LCP path.
- **The footer's `widths` / `sizes` pair stays pinned** to the real CSS box
  (`Footer.astro`, and `--footer-logo-size` in `footer.css` /
  `footer-brand.css`). Unpinning them is what previously had phones
  downloading a 144 KB variant for a 170px box.
- **No `filter: drop-shadow` on the new `<img>`** — hard rule 6, iOS Safari.
- An inline SVG crown removes one image request from every page. A PNG crown
  keeps it, at a few KB.
